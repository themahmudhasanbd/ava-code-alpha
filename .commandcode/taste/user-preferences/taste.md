# User Preferences
- Prefers thorough, comprehensive audits ("deep audit") over surface-level reviews — lists multiple issues at once and expects all to be addressed. Confidence: 0.8
- Expects a structured "final audit" phase before shipping that covers: logics, services, implementations, API integrations, and specific UI states (empty state, loading state, syncing state, error handling) — followed by a "final polish" cleanup pass (unused imports, dead code, debug statements). These are two distinct phases. Confidence: 0.8
- Wants analysis structured by severity (critical/high/medium) with concrete root causes, not just symptom descriptions. Confidence: 0.75
- Expects actionable fix proposals alongside bug reports — not just diagnosis but prioritized remediation steps. Confidence: 0.75
- When presented with a prioritized list of fixes, wants all implemented in one batch — brief "yes please" confirmation means go ahead with everything, no need for per-fix review. Confidence: 0.75
- Works on AvA — an AI agent platform with a Rust backend (ava-rs/) and multiple frontends; actively maintains the React Native mobile app (ava-mobile/) while migrating to Tauri 2 + React + TypeScript + Rust (ava-mobile/v2/). Confidence: 0.9
- Familiar with streaming state management concepts (agent turns, timeline, pending messages, heartbeat, reconnect) — communicates at a senior developer level despite informal typing. Confidence: 0.8
- Prefers single-command automated deploy via `deploy.sh` (git → build → deploy → health check) — expects the agent to find and run the deploy script, not do steps manually. Confidence: 0.85
- Uses conventional commit format (`fix(mobile):`, `feat:`, etc.) with descriptive bodies; deploy script auto-generates commit messages from the summary the user approves. Confidence: 0.7
- Strongly prefers collision-proof, unique IDs on all entities (messages, prompts, agent turns) — timestamp-based IDs are unacceptable; expects compound IDs (timestamp + sequence + random). Confidence: 0.9
- Demands explicit parent-child linking between related entities (e.g. user prompt → agent response via parentId) — relationships must be structurally encoded, not inferred by text matching. Confidence: 0.85
- Prioritizes data integrity over performance — expects multi-layer deduplication (by ID at merge, at coalesce, and at final output). Confidence: 0.8
- Communicates requirements in informal/broken English but provides precise, actionable technical specs — parse the intent, not the grammar. Confidence: 0.85
- Communicates in Bengali (Bangla) for task requests — expect Bangla messages for general directives (e.g. "check koro", "fix korso"); respond in English regardless of input language. Confidence: 0.85
- Reports immediately when a fix doesn't work and expects the agent to re-trace root causes more deeply rather than patch over symptoms again. Confidence: 0.8
- Expects static analysis (`flutter analyze` or `tsc --noEmit`) to be run and pass before any deploy — won't accept "it should compile" without proof. Applies to both Flutter and TypeScript/React Native projects. Confidence: 0.8
- Gives extremely terse instructions (a link + a short path) and expects the assistant to infer full context, fetch resources autonomously, and execute end-to-end without step-by-step guidance. Confidence: 0.85
- For large/greenfield projects, expects comprehensive upfront discovery and planning documentation (architecture, MVP scope, API contracts, UI spec, implementation plan, risk register, ADRs) before any code is written. Confidence: 0.8
- Organizes major rewrites in versioned subdirectories (e.g. `ava-mobilev2/`) rather than in-place upgrades. Confidence: 0.7
- Expects external design docs (Google Docs, specs) to be followed step-by-step as the authoritative source of truth — "read it and follow it" means implement exactly what the doc says, don't improvise. Confidence: 0.85
- Expects incremental git commits and pushes at each milestone or phase completion — don't accumulate all changes until the end; preserve progress in version control continuously. Confidence: 0.8
- Expects live-server integration testing as part of phase completion — providing a server URL means "test everything end-to-end against this server now," not just build/compile checks. Autonomous testing with script-based API verification (Python/websockets, curl) is expected. Confidence: 0.85
- When live-server testing reveals API contract bugs (e.g. param naming, response shape), expects immediate fixes + commit + push without asking permission — bugs found during testing are treated as blockers to close out. Confidence: 0.75
- Strongly opposes dark theme as default — UI should not force dark mode; use light theme unless explicitly told otherwise. Confidence: 0.9
- When rewriting/migrating an existing app, the new version MUST visually match the original's layout, theme, and component design — never improvise UI from scratch; study the existing codebase as the source of truth for all visual decisions. Confidence: 0.9
- Demands strict separation between "session" (chat) screen and "timeline" (debug/details) screen — session screen shows only clean final output; all intermediate streaming text, tool executions, and internal state belong exclusively in the timeline. Never leak internal/intermediate parts into the user-facing chat view. Confidence: 0.9
- Prefers tree-style hierarchical UI (with `├─` / `└─` connectors, indented sub-trees, left accent borders) for displaying agent execution details — ava/ava core is the reference pattern for this. Expects nested parent→child visual structure wherever agent streams have parts and parts have sub-events. Confidence: 0.85
- Prefers clean/minimal icon styling — no colored icon backgrounds; use neutral `COLORS.secondary` background with `COLORS.border` border, and let the icon itself carry the color (natural stroke color per type). Colored backgrounds look cluttered. Confidence: 0.85
- Strongly prefers reusing existing app components (e.g. `Tabs`/`TabsList`/`TabsTrigger` from `@/components/kit`) over hand-built custom implementations — always check the kit/ui library first before creating new UI elements. Confidence: 0.85
- Expects gesture-based navigation as complement to button navigation — e.g. swipe left to go back from detail screens (Timeline → Session). Uses `react-native-gesture-handler` `PanGestureHandler`. Confidence: 0.75
- Prefers distinct color-coded visual states for operation lifecycle (running/complete/failed) — color-coded borders, icon colors, progress bar colors, and summary stats should clearly communicate state at a glance. Confidence: 0.8
- Expects comprehensive stats in completion summaries — duration, tool count, plan progress, token count — shown as a dot-separated stats row when operations finish. Confidence: 0.75
- When migrating between frameworks (e.g. Flutter → React Native), expects ALL native platform features from the old app to be ported to the new one — not just UI/business logic but foreground services, boot receivers, native bridges, push notifications, etc. The old codebase is the feature checklist. Confidence: 0.85
- When porting features across frameworks, expects improvements and advancements ("advancement soho") — not just 1:1 parity but modernized implementations (e.g. better TypeScript types, cleaner APIs, proper error handling). Confidence: 0.8
- Prefers hub-and-spoke settings architecture — main Settings screen shows categorized navigation tiles (CONFIGURATION, SYSTEM, ACCOUNT sections) that lead to dedicated sub-settings screens (Notifications, Permissions, Models, Workspace, etc.). The hub should be a concise summary, not a wall of controls. Confidence: 0.85
- When implementing platform features (e.g. Firebase, push notifications), expects full-stack verification of both client-side and server-side integration status — don't just build the app side; audit whether the backend also has the required endpoints/services. Confidence: 0.8
- Expects operational management controls (start/stop/restart actions) in system monitoring screens — not just read-only status displays. PM2, systemd, service dashboards should all have actionable buttons to manage processes. Confidence: 0.8
- Expects app screens to provide two-way server configuration management — not just reading server state but also writing changes (model selection, reasoning effort, sandbox mode) back to the server via API. Screens should have explicit "Apply to Server" actions, not just local-only toggles. Confidence: 0.85
- When reviewing existing screens, expects audit of actual functional capability — "can this screen properly manage X?" means verify it has full CRUD/action flows, not just display. If management is missing, rebuild the screen with proper controls. Confidence: 0.8
- Expects security/permission policy controls (e.g. tool access policies, approval modes) as standard in management screens — not just operational actions (start/stop/restart) but also granular access/permission configuration. When building MCP or agent management screens, include policy selectors (auto/prompt/writes-only/approve-all) that write back to server config. Confidence: 0.75
- Expects two-way verification when implementing features: (1) audit what the backend/core actually provides (events, APIs, types) before building frontend, and (2) verify the final implementation compiles and is wired correctly (`npx tsc --noEmit` or equivalent). Never skip the gap analysis or the compilation check. Confidence: 0.85
- When asked to "verify all works correctly," expects running type-checking (tsc --noEmit) and tracing end-to-end data flows (API → state → UI) — not just visual review. Confidence: 0.8
- When asked to check if a screen can manage something, means audit for full CRUD/action capabilities (not just read-only display) and rebuild if management is missing. Confidence: 0.8
- Prefers native Android features to be ported from legacy app versions — the old codebase (v1 Flutter, etc.) serves as the feature checklist for what the new app must have. "Port with improvements" is the default expectation. Confidence: 0.85
- Prefers comprehensive Terminal screen with: control key bar (ESC, TAB, arrow keys, CTRL+C/D/L), symbol key bar (shell operators), command history navigation (▲/▼), multi-tab support, and shell badge showing active shell type. This matches the v1 Flutter terminal layout. Confidence: 0.8

- Expects MCP screens to support OAuth login flows (calling backend OAuth endpoints, opening browser for auth) as a first-class feature, not just server status display. Confidence: 0.75
